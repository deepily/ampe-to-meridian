# Meridian: GCP-Native Student Retention ML Pipeline

**Date**: 2026-04-01
**Status**: Plan approved, implementation not started
**Serialized from**: `~/.claude/plans/harmonic-swinging-pelican.md`

## Context

**Problem**: The [AMPE repo](/mnt/DATA01/include/www.deepily.ai/projects/ampe) is a mature but artisanal ML pipeline framework for student retention prediction. It's AWS-centric (Redshift, S3, MLflow), Docker-based, with zero GCP-native services. The FDE competency gap analysis ([2026.03.31-fde-competency-product-gap-analysis.md](/mnt/DATA01/include/www.deepily.ai/projects/google/fde-prep/src/rnd/2026.03.31-fde-competency-product-gap-analysis.md)) identified 3 CRITICAL weak competencies and 12 MODERATE gaps -- nearly all addressable by replacing AMPE's components with GCP equivalents.

**Outcome**: A new project called **Meridian** that reimplements AMPE's 7-stage ML pipeline using GCP managed services, targeting all 15 gap competencies. Lives at `src/ampe-gcp/` initially, later moves to its own repo.

**Prior work to build on** (from TODO.md, completed 2026-03-31):
- Cloud Monitoring/Logging/Trace/Alerting already implemented in talking-tractor
- IAP + Global LB multi-region design doc exists
- Vertex AI Pipelines design doc for lupin PEFT trainer exists
- GitHub Actions CI/CD plan for lupin exists

These inform patterns but Meridian implements its own versions for the student retention domain.

## What AMPE Does (replacement targets)

| AMPE Stage | Current Implementation | Meridian GCP Replacement |
|---|---|---|
| Data ingest | SQL -> Redshift/MySQL, cached locally | BigQuery client, GCS staging |
| Harmonization | Column mapping via metadata | Pipeline component (same logic, KFP wrapper) |
| Cleaning | Null removal, OHE, string encoding | Pipeline component + TFDV validation |
| Feature engineering | Date deltas, binning, MVE, chi-square | Pipeline component + Feature Store sync |
| Dimensionality reduction | Correlation culling, VIF analysis | Pipeline component (same algorithms) |
| Model build | 6 sklearn/XGB algorithms, SMOTE, grid search | Vertex AI Training + Vizier tuning |
| Model competition | Compare TP/TN rates, select best | Evaluate component + Experiments logging |
| Post-modeling | MLflow, SHAP, predictions -> S3/Redshift | Vertex AI Experiments, Explainable AI, Model Registry |
| Config system | INI with `@_default_*` inheritance | Pydantic + YAML with env override hierarchy |
| Credentials | JSON files on disk | Secret Manager + Workload Identity |
| Storage | S3 (`s3fs`) | GCS with CMEK + lifecycle policies |
| Experiment tracking | MLflow | Vertex AI Experiments + TensorBoard |
| Serving | None (batch only) | Vertex AI Prediction + Cloud Endpoints |
| Monitoring | None | Vertex AI Model Monitoring (drift/skew) |

## Data Synthesis Strategy

Since AMPE uses real institutional student data from Redshift, Meridian needs synthetic data that mirrors the schema.

**4 BigQuery tables, modeled from AMPE's `foo-config.ini` columns:**

| Table | Rows | Key Fields | PII for DLP |
|---|---|---|---|
| `student_demographics` | 50,000 | student_id, hs_gpa, sat_score, campus_latitude/longitude, first_generation_flag | first_name, last_name, email, ssn_last4 |
| `academic_records` | 200,000 | student_id, term, term_gpa, cumulative_gpa, credits_attempted/earned, major | -- |
| `financial_aid` | 50,000 | student_id, efc, pell_eligible, total_aid, loan_amount, unmet_need | fafsa_filed_date |
| `enrollment_events` | 150,000 | student_id, event_type, event_date, enrollment_status, **second_year_ret_flag** (target) | -- |

**Generation approach:**
- `faker` for PII fields (names, emails, synthetic SSNs)
- `numpy` for correlated distributions (GPA <-> retention r ~= 0.4, financial need <-> retention r ~= -0.25)
- 75% retained / 25% not retained (realistic class imbalance for SMOTE)
- 15% of records have SSN patterns in a `notes` field, 5% have phone numbers in `address_line2` -> gives Cloud DLP real work
- 2-3% deliberate data quality issues (null GPAs, out-of-range SATs) -> TFDV catches these

## Phased Implementation Plan

### Phase 1: Foundation + Synthetic Data (Days 1-3)

**Build:**
- Project scaffolding, `pyproject.toml`, `CLAUDE.md`
- Terraform modules: `bigquery` (CMEK, partitioned by term), `storage` (lifecycle: Standard->Nearline->Coldline->Archive), `security` (KMS key ring, Secret Manager, IAM service accounts), `networking` (VPC, VPC Service Controls in dry-run)
- Synthetic data generator (50K students, 4 tables, PII, deliberate quality issues)
- Load into BigQuery + GCS
- ADRs 001-004

**Competencies**: Data Protection & Privacy, Infrastructure & Network Security, Compliance & Governance, Resource Efficiency, Infrastructure as Code

### Phase 2: Pipeline Core + Data Protection (Days 4-8)

**Build:**
- Vertex AI Pipeline (KFP v2 DSL) -- the DAG mapping AMPE's 7 stages to 14 components
- Components: `ingest`, `validate` (TFDV), `dlp_scan` (Cloud DLP), `harmonize`, `clean`, `feature_engineer`, `feature_store_sync`, `reduce_dimensions`
- Cloud DLP scan on student data -- detect/redact PII (FERPA compliance)
- TFDV schema generation + anomaly detection (catches the 2-3% quality issues)
- Vertex AI Experiments integration (each pipeline run -> experiment)
- Vertex AI Feature Store: Student + Course entity types
- Structured Cloud Logging + Cloud Trace spans throughout

**Competencies**: **AI Lifecycle Management (CRITICAL)**, **AI-Specific Security (CRITICAL)**, **Failure & Recovery Testing (CRITICAL)**, Observability, Extensibility

### Phase 3: Training + Competition + Explainability (Days 9-13)

**Build:**
- `train` component: preserves AMPE's GenericModel pattern -- 6 algorithms (XGBoost, RF, LR, AdaBoost, DT, GB), SMOTE iteration
- `tune` component: Vertex AI Vizier Bayesian search (replaces sklearn ParameterSampler)
- `evaluate` component: model competition (compare TP/TN rates), log to Experiments + TensorBoard
- `explain` component: Vertex Explainable AI (Sampled Shapley for tabular)
- `register` component: Vertex AI Model Registry with metadata + model card
- ML unit tests: output shapes, label leakage detection, gradient sanity
- `docs/model-card.md` -- Responsible AI model card

**Competencies**: **AI Lifecycle Management (CRITICAL)**, **AI-Specific Security (CRITICAL)**, **Failure & Recovery Testing (CRITICAL)**, Configuration Management

### Phase 4: Serving + Degradation + Monitoring (Days 14-18)

**Build:**
- `deploy` component: Vertex AI Prediction endpoint with traffic splitting (A/B)
- Custom prediction container (FastAPI) with Cloud Endpoints OpenAPI spec
- Memorystore Redis cache for frequent predictions (top 50 common student profiles)
- Graceful degradation: endpoint down -> cache -> batch predictions -> "service degraded"
- Vertex AI Model Monitoring: prediction drift, data drift, training-serving skew
- Pub/Sub + Cloud Function: drift alert -> trigger retraining pipeline
- Cloud Armor WAF rules on prediction endpoint via GLB
- Cloud Monitoring dashboard + alerting policies

**Competencies**: Availability Design, Graceful Degradation, API Design & Versioning, API Documentation, Observability, Extensibility, Authentication & Authorization

### Phase 5: CI/CD + Chaos Testing + Polish (Days 19-22)

**Build:**
- Cloud Build pipeline: lint -> test -> build containers -> deploy infra -> run pipeline -> validate
- GitHub Actions workflow (mirrors Cloud Build)
- Chaos tests: inject drift -> verify monitoring alert -> verify retraining triggers
- Chaos tests: kill prediction endpoint -> verify cache fallback
- Chaos tests: corrupt input data -> verify TFDV blocks pipeline
- Cloud Audit Logs verification
- VPC Service Controls: promote from dry-run to enforced
- Final docs: `architecture.md`, `runbook.md`, remaining ADRs
- Workload Identity Federation for CI/CD (no JSON key files)

**Competencies**: **Failure & Recovery Testing (CRITICAL)**, CI/CD & Deployment, Compliance & Governance
